# עוזר הגמ"ח

בוט ששואלים אותו על מסמכי ארגון, והוא עונה רק מתוכם (RAG). הארגון, "גמ"ח אור החסד", והמסמכים בתיקיית `data` בדויים.

## הרצה
נבדק על Python 3.12.

```bash
python -m venv .venv
.venv\Scripts\activate          # ב-Mac/Linux: source .venv/bin/activate
pip install -r requirements.txt
copy .env.example .env          # ב-Mac/Linux: cp, ואז להכניס OPENAI_API_KEY
streamlit run app.py
```

בהפעלה הראשונה המאגר נבנה אוטומטית. אחרי שינוי מסמכים: הכפתור "בניית המאגר מחדש" או `python ingest.py`.
בדיקות ללא מפתח: `pip install pytest` ואז `pytest tests`.

## הקבצים
| קובץ | תפקיד |
|---|---|
| `config.py` | כל ההחלטות והפרמטרים |
| `ingest.py` | מסמכים ← Chunks ← וקטורים ← ChromaDB |
| `rag.py` | הרחבה ← Embedding ← MMR ← פרומפט ← תשובה |
| `app.py`, `style.css` | הקליינט ב-Streamlit |

## התהליך
**Ingestion:** קריאת הקבצים ב-LlamaIndex ← חלוקה ל-512 טוקנים עם חפיפה של 50 ← `text-embedding-3-small` ← שמירה ב-ChromaDB.

**Query:** שאלה ← הרחבה אם יש פחות מ-5 מילים ← Embedding ← בדיקת סף דמיון ← MMR מחזיר 5 קטעים ← פרומפט עם הוראות, קטעים והשאלה המקורית ← `gpt-4o-mini` ← תשובה ומקורות.

## ההחלטות
| # | נושא | בחירה | נימוק |
|---|---|---|---|
| 1 | Vector DB | ChromaDB | רץ מקומית, שומר לדיסק, מתאים לנפח קטן |
| 2 | ספרייה | LlamaIndex | דרישת התרגיל |
| 3 | חלוקה | לפי טוקנים, 512 | שליטה בגודל ובעלות, ללא קריאות AI בחלוקה |
| 4 | חפיפה | 50 טוקנים | שומרת משפט שנחתך בגבול בין Chunks |
| 5 | ספק | OpenAI בתשלום | מחיר נמוך ושני המודלים אצל ספק אחד |
| 6 | Top K | 5 | כיסוי טוב בלי יותר מדי רעש |
| 7 | מודלים | `text-embedding-3-small`, `gpt-4o-mini` | זולים ומספיקים לשאלות על מסמכים |
| 8 | הרחבת שאלה | רק מתחת ל-5 מילים | עוזרת לשאלה מקוצרת בלי לשלם על כל שאלה |
| 9 | חיפוש | MMR מתוך 15 מועמדים | מונע החזרת קטעים כמעט זהים |

**הגנה מהמצאות, בשתי שכבות:** סף דמיון שעוצר לפני המודל, והוראה בפרומפט לענות רק מהקטעים.

## 3 בעיות ופתרונן

**1. Chunk של 20,000 טוקנים**
הבעיה: בתכנון בחרתי גודל של 20,000 טוקנים, אבל מודל ה-Embedding מקבל כ-8,000 טוקנים בקלט, ו-Chunk כזה מערבב נושאים רבים בווקטור אחד.
הפתרון: מדדתי כמה טוקנים תופסת מילה בעברית, ועברתי ל-512 טוקנים עם חפיפה של 50.

**2. סף הדמיון לא עבד עם MMR**
הבעיה: הציון ש-MMR מחזיר כולל קנס על דמיון לקטעים שכבר נבחרו, ולכן קטע רלוונטי יכול לקבל ציון נמוך. בנוסף, ChromaDB משתמש כברירת מחדל במרחק L2, שאינו נותן סקאלה של דמיון קוסינוס.
הפתרון: יצרתי את הקולקציה עם `hnsw:space=cosine`, ואני מחשבת דמיון קוסינוס בנפרד ובודקת עליו את הסף. MMR משמש רק לבחירת הקטעים.

**3. ה-CSS הוצג כטקסט ו-RTL שבר את המובייל**
הבעיה: שורה ריקה בתוך `<style>` ב-`st.markdown` גרמה ל-CSS להופיע על המסך. בנוסף, `direction:rtl` על שורש האפליקציה הפך את הסרגל הצדדי במובייל לפס צר שהסתיר את התוכן.
הפתרון: העברתי את העיצוב ל-`style.css` וטענתי אותו ב-`st.html`, והחלתי RTL רק על אזורי התוכן.

## שאלות לראיון
**מה קורה כשהשאלה לא קשורה למסמכים?** Top K תמיד מחזיר קטעים, גם רחוקים. לכן יש סף דמיון, והפרומפט מחייב לומר שאין מידע.

**מתי בונים את האינדקס מחדש?** כשמשתנים המסמכים, גודל ה-Chunk, החפיפה או מודל ה-Embedding. החלפת מודל התשובה, Top K או צורת החיפוש לא מחייבת בנייה מחדש.

**למה מודלים שונים?** מודל Embedding הופך טקסט לווקטור לחיפוש, ומודל השפה כותב את התשובה.

**למה MMR ולא Top K רגיל?** בגלל החפיפה קטעים סמוכים דומים. MMR מאזן בין קרבה לשאלה לבין שוני מהקטעים שכבר נבחרו.

**למה ההרחבה לא נשלחת למודל התשובה?** היא נועדה לחיפוש בלבד. הלקוח צריך לקבל מענה על מה ששאל בפועל.

**מה החיסרון של חלוקה לפי טוקנים?** היא עלולה לחתוך באמצע רעיון, ולכן יש חפיפה.

**מה הייתי משפרת?** זיכרון שיחה, חיפוש היברידי למספרים ומונחים מדויקים, Reranker, ומדידת איכות על סט שאלות קבוע.

## מגבלות
